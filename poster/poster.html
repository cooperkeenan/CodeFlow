CodeFlow: Intuitive Codebase Maps

Living documentation for your codebase

Cooper Keenan

Developers spend more time reading unfamiliar code than writing it, yet the diagrams meant to help show structure — which file imports which — rather than behaviour. A call graph answers "who calls whom". It does not answer "what happens when a request arrives".

CodeFlow takes a Python repository and produces a single-page diagram of what the system does when it runs: where requests enter, which branches genuinely change the outcome, and what the system writes to. Deterministic static analysis owns every node and edge; a temperature-zero language model only judges which branches matter and names them in human language. The pipeline is byte-identical across runs and every node carries a file:line reference, so a structural hallucination is impossible by construction rather than merely unlikely.

1Introduction

The problem. Comprehension is the dominant cost in software work. Onboarding amplifies it, and written documentation rots away from the code it describes.

The gap. Comment-based generators need annotations that nobody writes. Tools such as PlantUML and Structurizr need the diagram authored by hand, so it is only ever as current as its author. Tools that hand a whole repository to a language model produce output that is plausible and confidently wrong, because nothing constrains the model to structure that actually exists.

Aim. Given only a repository, produce an accurate, readable, single-page diagram of what the system does when it runs.

Objectives

  1. Derive structure deterministically by static analysis, with no model influence over nodes or edges.
  2. Identify architecturally meaningful branch points and separate them from trivial guards.
  3. Render a bounded one-page view — entry, decision, effect — with services as swimlanes and cross-service calls stitched into one journey.
  4. Constrain the model to judging and naming only, validated against ids the pipeline issued.
  5. Deliver a usable product: web UI, GitHub sign-in, persistence, CI integration.
  6. Evaluate accuracy, determinism and utility.

2Method: architecture

A FastAPI gateway, five agent services and a React frontend, with a typed contract on every hop, so each stage can be tested and replaced on its own. The tracer runs eight stages over the source tree, and only one of them — judging which forks are real — ever calls a model.

3Method: which branches matter

Most branches in real code are noise. The hard problem is telling a decision — a fork that sends the system somewhere genuinely different — from a guard that checks a value and rejoins the same path.

if s is None: Guard. Both arms rejoin the same work. Not something a person would draw.
if s == "cat": Decision. The arms reach materially different downstream work.

The test is reach-set mutual exclusivity: compute what each arm can reach, and admit the fork only when the arms fail to reconverge. Seven detectors find candidate forks — branch, match, except, table, route, polymorphic and dynamic dispatch. Dispatch that cannot be resolved is drawn as dynamic, never guessed.

4Facts vs interpretation

Static analysis owns The model may only
  • Module boundaries
  • The symbol table
  • The call graph, with the branch arm each call sits under
  • Dispatch sites and effects
  • Significance ranking
  • Condensation and the page budget
  • All geometry
  • Judge a ranked fork: decision, guard or noise
  • Name a node in human language
  • At temperature zero, cached by content
  • Keyed to ids the pipeline issued
  • Validated, with a deterministic fallback if it fails

The model never adds a node or an edge. It cannot invent a component that is not in the source, because it is never asked for one.

7Conclusion

Objectives 1, 2, 3 and 5 are met. Objective 4 was revised rather than met: the model was meant to name only, but separating decisions from guards proved to need judgement that no heuristic reproduced, so the model was given that verdict too — still with no power to add structure. Objective 6 is partially met: determinism and grounding are measured, but accuracy against a hand-derived ground truth, and comparison against a raw call graph and a one-shot model baseline, are designed and not yet run — so no accuracy figure is claimed here.

Limitations

  • Tracing is Python-only, so the React frontend is invisible and no frontend → api call is ever stitched.
  • The page budget is apportioned by lane mass, letting a route-heavy service crowd others out.
  • CodeFlow itself is nearly linear, so the self-run under-sells the feature — which is why the figures above use a third-party repository.

8Further work

  • Cross-repository maps, so a call that leaves one service can be followed into the next instead of stopping at the repository boundary.
  • Infrastructure as code: read a Terraform or Pulumi repository and draw the resources it provisions, beside the code that provisions them.
  • Editable diagrams (in progress), letting a reader correct or annotate a map and keep the correction.
  • Change proposals: draw a change before writing it, so the diagram becomes the brief you hand to a language model.
